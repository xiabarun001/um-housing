# ADR-002：档案信息走"采集 → 评估 → 人审 → 发布 → 留痕"的流水线

## 状态

已采纳。**日期：** 2026-09-08 **决定人：** Sasha、Claude

## 背景

档案信息（设施、年份、户数、地契、坐标）目前靠人翻 iProperty 和开发商网页核对，没有留下来源和时间，也没有办法知道什么时候该复核。要扩到 25 个小区、每月复核一次，并让管理员每月人工不超过 2 小时，就需要机器做重复劳动、人只做判断。同时行情信息已经有一条自动流水线（`scripts/refresh.mjs` + GitHub Actions），证明"curl 加浏览器指纹"从 GitHub 和本机都能抓到 iProperty，PropertyGuru 用 iOS Safari 指纹也能抓。

## 决定

我们为档案信息建一条独立于行情的流水线，规则如下：

1. **采集（collect）**：`scripts/collect.mjs <id 或项目链接>` 抓 iProperty 项目页（一手来源）和 PropertyGuru 项目页（二手核对），把字段、原始值、来源链接、时间写进 `data/staging/<id>.json`。行情脚本不动档案，档案脚本不动行情。
2. **评估（assess）**：每个字段按两源结果标「一致」「单源」「冲突」；和现有 `condos.json` 比较标「无变化」「新值」「新增」。交叉验证的来源按字段定（`scripts/crosscheck.mjs`）：
   - 坐标：iProperty 项目页 vs OpenStreetMap（Nominatim 按小区名地理编码），相差 < 150 m 为一致，150–600 m 为接近，再远为冲突。
   - 步行距离和分钟：现有值 vs OpenStreetMap 路网上的步行路线（Valhalla 公共服务，免费无密钥），相差 25% 以内为一致；标"估"的估算值可用 `--accept=walk` 直接采纳路线值，方式记为 `route`。
   - 年份、户数、地契、开发商、设施：iProperty 项目页是主来源。2026-09-08 核实 PropertyGuru 马来西亚站和 iProperty 是同一集团、同一数据库（页面结构、项目编号完全一致），**不能当独立二源**。独立二源只能靠开发商官网、StarProperty、PropWall 等（能否抓取见 probe 记录），否则标「单源」。
   - 行情：iProperty 挂牌 vs Mudah（整套按 buildingName 精确匹配、单间按标题匹配，最低价相差 35% 以内算一致；结果在 prices.json 的 check.mudah）和 iBilik（区域 2）。
   每个字段的核对结果写进 `provenance.<字段>.check`（对方来源、结论、差值、时间），页面的档案标记弹层里能看到。
3. **报告（review）**：生成 `data/staging/REVIEW.md`，按小区列出差异和评估结论，附建议动作。管理员只看这份报告。
4. **发布（publish）**：`scripts/publish.mjs <id> [--accept 字段,字段]` 把接受的字段写入 `condos.json`，写 `provenance` 和 `verified_at`，追加一条 `data/changelog.json`（谁、何时、改了什么、来源、理由、对外说明）。同一份记录两个视图：读者页只显示日期、小区和对外说明；后台显示全部。
5. **不自动发布档案**：GitHub Actions 每 30 天全量采集，只提交 staging 和报告；发布必须由人执行（本机命令或后台按钮）。
6. **新增小区**：只需项目链接，采集产出完整 staging 记录；区域、编号、别名由人补。
7. **读者纠错**进入同一条流水线：Supabase `reports` 表里的反馈在后台展示，处理时同样走 publish 留痕。

来源优先级固定为：开发商官网 > iProperty 项目页 > PropertyGuru 项目页 > 平台挂牌帖 > 小红书帖子。

## 后果

### 好处

- 人只做判断，不做抄写；每月工时可控。
- 每次变更有来源、时间、理由，可追溯、可回滚。
- 双源一致率成为可衡量的质量指标。
- 区域 3 和以后任何新增小区都走同一条路，质量不随扩容下降。

### 代价

- 多两个脚本和一个 staging 目录要维护；页面结构变了要跟着修解析。
- 二源冲突需要人裁决，报告里要把理由写清，否则下次还会冲突。

### 中性

- 行情流水线保持不变，只是共用抓取函数。
- staging 和 changelog 进仓库，公开可见，也是"我们先做的"证据。

## 备选方案

- **全自动发布档案**：省人工，但一次解析错误就把错误发布出去，和"百分百可信"的目标冲突。否决。
- **把数据搬进 Supabase 表，后台直接改库**：省掉 git 提交，但失去历史和回滚，网站读取也从静态变成依赖数据库可用性。否决，保留 git 为唯一真源。
- **继续人工核对**：现在能撑，25 个小区每月一次就撑不住，且无留痕。否决。
