# ADR-003：管理后台 UMH Console 用邮箱验证码登录、Pages Functions 写入

## 状态

已采纳并实现（2026-09-08 夜）。**日期：** 2026-09-08 **决定人：** Sasha、Claude

## 背景

Sasha 要一个只有管理员能登录的后台（不需要注册，只有登录），把小红书出图、采集审核、纠错处理、意向表管理都收进去。网站是静态站，托管在 Cloudflare Pages，数据在 GitHub 仓库里，意向表在 Supabase。约束：不想花钱，不想自己保管密码，不想把数据从 git 搬走。

## 决定

后台叫 **UMH Console**（简称 UMHC），路径 `/console/`。

- **登录**：Supabase Auth 的邮箱一次性验证码（2026-09-10 定；原方案 Cloudflare Access 要绑卡，放弃）。白名单放在 Pages 环境变量 `ADMIN_EMAILS`，发码前就比对，名单外的邮箱收不到信；token 存 HttpOnly cookie，`/console/*` 和 `/api/*` 每次请求都再验一次。没有注册页，没有密码，从名单里删掉即失效。
- **读取**：后台页面本身是静态页，读取仓库里的 JSON、staging、changelog，和读者页一样。
- **写入**：需要改数据的动作通过 Cloudflare Pages Functions 完成，Function 先校验 Access 的 JWT（签名、受众、有效期）。意向表用存在 Pages 密钥里的 Supabase service key 直接操作。**改仓库数据不由 Function 直接写文件**，而是用 GitHub token（只限本仓库 Actions: write）触发 `console-action.yml`，让云端跑同一套 `publish.mjs` / `arbitrate.mjs` / `collect.mjs` / `refresh.mjs` 并提交——后台和命令行走同一条路，留痕规则不会分叉。浏览器永远拿不到这两个密钥。（实现时相对提案的唯一调整：写仓库改为触发工作流，而不是 Function 直接提交 JSON。）
- **出图**：v1 从后台链接到现有 `cards.html`（未收录、不索引），迁入 `/console/` 留到下一版。
- **v1 页面**：总览、采集与审核、小区档案、纠错、意向表、出图、日志，共七个，不多做。

## 后果

### 好处

- 零密码代码，零注册逻辑，安全边界交给 Cloudflare。
- 数据仍在 git，每次后台操作都是一次有作者和时间的提交，可回滚。
- 静态站的性能和防护不变，后台只是多了几个页面和几个 Function。

### 代价

- Access 应用和白名单要 Sasha 在 Cloudflare 控制台配置一次；GitHub token 要生成并存为密钥。
- Pages Functions 是 Cloudflare 特有的，换托管商要重写这部分（量很小）。
- 每次发布都是一次仓库提交并触发部署，约一分钟后生效，不是即时。

### 中性

- 意向表的删除从"口令"改为后台按钮，口令方式可保留作为兜底。
- 以后要加管理员，只是在白名单里加邮箱。

## 备选方案

- **Supabase Auth 邮箱密码登录，数据搬进 Supabase 表**：功能完整，但要自己处理密码找回和会话，数据离开 git 失去历史，网站读取依赖数据库。否决。
- **自己写用户名密码登录**：要保管密码哈希、防暴力破解、做找回流程，风险和工作量都不值。否决。
- **只用 GitHub 网页直接改 JSON**：零开发，但对不熟 git 的同学门槛高，也没有审核视图。作为过渡可以，不是终态。
