# PRD：UM 租房指南 2.0

覆盖三个区域、信息分层、采集审核、管理后台。读完约 12 分钟。配套决策记录：[ADR-001 信息分层](ADR-001-信息分层.md)、[ADR-002 采集与审核流水线](ADR-002-采集与审核.md)、[ADR-003 管理后台](ADR-003-管理后台.md)。

## 1. 概述

### 问题

> 2026-09-09 变更：出图功能（cards.html）已删除，下文叙述里出现的"出图"是当时的背景，不再是要做的事。

网站已经上线（um-housing.evasuka.com）：19 个小区、两个区域、价格每 12 小时自动更新、同学意向表、小红书出图页。接下来遇到五个问题：

1. **区域 3 缺失。** 小红书上流传的分区图有三个区域（PJ 一侧、Bangsar South 一侧、Seputeh / Old Klang Road 一侧），来的人会问第三片。
2. **可信度看不出来。** 页面上"2017 年建成"和"单间 RM 650 起"长得一样，读者分不清前者是核实过的事实、后者是随时会变的挂牌价。管理员也没有一个清单说明每个数字从哪来、什么时候核的。
3. **固定信息没有流程。** 19 个小区的设施、年份、户数靠人翻网页核对，没有留来源和时间，扩到 25 个小区、每月复核一次就撑不住。
4. **维护入口分散。** 核数据在本地脚本，删意向表在 Supabase 控制台，出图在一个隐藏页面，改数据要会用 git。管理员没有一个登录后的工作台。
5. **盗用风险。** 已有授权声明、水印、指纹，但"哪些是我们独有的、可持续更新的"需要被流程保证，而不是靠一次性整理。

### 方案摘要

四个模块，按依赖顺序建：

1. **三层信息模型**：把所有数据分成「固定信息」「实时信息」「观点」三层，数据文件、页面标记、后台都按这三层组织（[ADR-001](ADR-001-信息分层.md)）。
2. **采集与审核流水线**：采集 → 校验 → 评估 → 审核 → 发布 → 留痕，档案类信息只能经审核后发布（[ADR-002](ADR-002-采集与审核.md)）。
3. **区域 3**：作为流水线的第一个用例上线，6 个小区。
4. **管理后台 UMH Console**：只登录、不注册，把采集审核、纠错、意向表、出图收进一个工作台（[ADR-003](ADR-003-管理后台.md)，放在最后做）。

### 用户

| 角色 | 谁 | 场景 | 设备 |
|---|---|---|---|
| 读者 | 来 UM 读书、校外租房的新生，主要从小红书进来 | 想清楚要什么 → 看小区 → 找中介 → 签约 | 手机为主 |
| 管理员 | Sasha 和 1–2 位同学 | 复核档案、审核采集结果、处理纠错、管意向表 | 电脑 |

## 2. 目标与指标

### 目标

1. 每一个数字都能回答"从哪来、什么时候、能不能信"。
2. 维护成本可控：管理员每月人工 ≤ 2 小时。
3. 覆盖三个区域 25 个小区，信息质量不因扩容下降。
4. 管理动作有一个登录后的入口。

### 指标

| 指标 | 现状 | 目标 | 何时看 |
|---|---|---|---|
| 行情新鲜度：页面显示的行情距抓取 ≤ 24 小时的小区占比 | 19/19 | 25/25 | P2 上线后持续 |
| 档案复核：每条档案距上次核实 ≤ 45 天且有记录 | 有日期无记录 | 100% | P2 后 60 天 |
| 双源一致：档案字段有两个来源且一致的比例 | 0（单源） | ≥ 80% | P2 |
| 纠错处理：读者反馈 7 天内处理完 | 无渠道 | ≥ 90% | P3 |
| 管理员月工时 | 未统计 | ≤ 2 小时 | P4 后 |

### 不做的事

- 不做用户注册、评论区、私信。
- 不做房源交易、中介撮合、任何收费。
- 不扩到全吉隆坡；只做 UM 周边三个区域。
- 不做原生 App。

## 5. 方案设计

### 5.1 信息架构

**站点结构**

```
/                指南（读者）
  先想清楚 → 1 地形 → 2 预算 → 3 挑候选 → 4 逐个看 → 5 找中介 → 6 看房签约 → 7 时间表 → 意向表 → 说明
/console/        管理后台 UMH Console（管理员，登录后可进）
  总览 · 采集与审核 · 小区档案 · 纠错 · 意向表 · 日志
```

**标签原则**：用读者的词，不用工程词。三层叫「固定信息」「实时信息」「观点」，不叫 static / dynamic / estimate。导航深度不超过 3 层。每个数字旁边都有层级标记，标记形状和颜色固定，不只靠颜色区分。

**内容模型（三层）**

| 层 | 含义 | 典型字段 | 来源 | 更新方式 | 页面标记 | 文件 |
|---|---|---|---|---|---|---|
| **固定信息** | 不会变或很少变的事实 | 开发商、地址、坐标、建成年份、户数、楼层、地契、类型、设施清单、最近轨道站、实测步行分钟、链接 | 开发商官网、iProperty / PropertyGuru 项目页、实地 | 流水线采集 + 人工审核；每 30–45 天复核 | 绿色实心点「固定信息 · 核实于 日期」 | `data/condos.json` |
| **实时信息** | 随市场变的数字 | 在租数量、整套最低价、各房型最低价、单间行情 | iProperty、iBilik 挂牌 | 机器每 12 小时 | 琥珀色实心点「实时信息 · 抓取于 时间」 | `data/prices.json`、`data/price-history.json` |
| **观点** | 我们的估算或主观评价 | 吃饭购物方便度、安静程度、估算的步行分钟、区域适合人群 | 直线距离估算、住户评价、我们的判断 | 人工，随复核更新 | 灰色空心点「观点」 | `condos.json` 里的 `judgment` 子对象 |

每条档案记录带 `provenance`：每个字段的来源链接、获取时间、方式（自动 / 人工 / 实地），以及整条记录的 `verified_at`。

### 5.2 功能需求

**A. 信息分层展示**

- FR-1 小区卡片、详情弹窗、地图侧栏、排行榜里的每个数据块都带层级标记和时间。
- FR-2 顶部徽章拆成三个胶囊：档案核实于、行情抓取于、判断说明。
- FR-3 「说明」板块重写为三段：可以直接信的、要注意的及原因、我们的判断。
- FR-4 行情超过 36 小时未更新时，标记变为「已 X 小时未更新」。
- FR-5 「先想清楚」里用到判断类字段的项标注「粗略」。
- FR-6 点标记能看到来源链接和时间（弹层或详情）。

**B. 采集与审核**

- FR-7 `node scripts/collect.mjs <id 或 iProperty 项目链接>`：抓取档案字段，写入 `data/staging/<id>.json`，含来源、时间、原始值。
- FR-8 交叉验证：坐标对 OpenStreetMap，步行距离对 OSM 路网步行路线，年份/户数/地契/开发商/层数/泳池健身房对 StarProperty 楼盘页（星报集团，和 iProperty 不同库；PropertyGuru 与 iProperty 同库，不算），实时信息对 Mudah 和 iBilik；每个字段评估为「一致」「接近」「单源」「冲突」，结果写进 provenance 并在页面标记弹层显示。两源冲突由人用 arbitrate.mjs 写结论和理由，页面显示理由，健康检查不再告警。
- FR-9 生成 `data/staging/REVIEW.md`：现有值、采集值、二源值、评估结论、建议动作，一眼能审。
- FR-10 `node scripts/publish.mjs <id>` 把审核通过的字段写入 `condos.json`，更新 provenance 和 `verified_at`，追加 `data/changelog.json`（每条含 at、who、condo、field、from、to、source、reason、public_note）。
- FR-10b 读者页「说明」下方显示对外版变更记录：只列日期、小区、"更新了什么"（public_note），不显示人。后台显示完整字段。
- FR-11 GitHub Actions 每 30 天对全部小区跑一次采集，只出报告，不自动发布。档案变更必须人审。
- FR-12 新增小区只需项目链接：生成完整 staging 记录，坐标自动取，区域和编号由人定。
- FR-13 读者纠错：卡片上「反馈」按钮 → Supabase `reports` 表（小区、字段、说明、可选联系方式），后台可见。

**C. 区域 3**

- FR-14 新增「区域 3 · Seputeh / Old Klang Road 一侧」：Avara Seputeh、Tria Seputeh、Vivo Residential Suites、Southbank Residence、Avantas Residences、Millerz Square，编号 20–25。
- FR-15 交通如实写：没有步行可达轨道站的，写清靠什么（KTM Seputeh、公交、Grab）和到 UM 的车程范围；实测前标「观点」。
- FR-16 地图、排行榜自动包含区域 3，颜色用第三色。

**D. 管理后台 UMH Console（最后做）**

- FR-17 路径 `/console/`，登录页 `/login/`，Supabase 邮箱一次性验证码，白名单邮箱，无注册，无密码。
- FR-18 总览：行情新鲜度、档案复核到期、待审核数、未处理纠错。
- FR-19 采集与审核：看 staging 差异，逐字段接受或拒绝，一键发布（Pages Function 调 GitHub API 提交）。
- FR-20 意向表：查看、删除（替代口令方式）；纠错：处理、关闭。

### 5.3 体验与视觉

- 标记系统：三种形状加颜色加文字（实心绿点、实心琥珀点、空心灰点），窄屏不换行不遮挡。
- 每个数字都能追溯：点标记看来源和时间。
- 首屏两句话说清三层的区别，不用术语。
- 视觉延续现有主题（纸感底色、白卡片、橙色章节线）。后台用同一套设计变量，布局改为工作台（左侧导航 + 表格 + 差异视图），目标是看得清、点得准。
- 手机端每个改动都要看一遍。

### 5.4 边界情况

| 情况 | 期望行为 |
|---|---|
| 采集时 iProperty 改版或 403 | staging 标 `fetch_failed`，报告列出，现有值不动 |
| 二源冲突（如户数不同） | 评估「冲突」，报告高亮，人工选一个并写理由，理由进 changelog |
| 行情连续失败 | 页面标记显示「已 X 小时未更新」，不显示假时间 |
| 新小区没有 StarProperty 页，或 StarProperty 是只有地契的新版页 | 评估「单源」，页面标记同样显示 |
| 纠错被刷 | Supabase 触发器限速，后台可批量删除 |
| 管理员邮箱泄露 | Access 白名单加一次性验证码，撤销邮箱即失效 |

## 6. 技术考虑

- 保持静态站加 Cloudflare Pages。数据留在 git，可审计、可回滚；后台的写操作走 Pages Functions 调 GitHub API，token 存为 Pages 密钥，浏览器拿不到。
- 采集脚本复用现有 refresh.mjs 的 curl / curl-impersonate 方式；StarProperty 楼盘页本机 curl 可抓，新版页以 HTTP 404 返回完整页面（软 404），页面够大就照样解析。
- 意向表和纠错继续用 Supabase 匿名插入加 RLS；后台通过 Function 内的 service key 操作，不暴露。
- 三层模型的字段约定见 ADR-001；流水线见 ADR-002；后台见 ADR-003。

## 10. 执行契约

- 权威来源优先级：开发商官网 / 实地 > iProperty 项目页 > StarProperty 楼盘页 > 平台挂牌帖 > 小红书帖子。冲突时以高优先级为准，用 arbitrate.mjs 记录结论和理由。
- 不可触碰：`prices.json` 不手改；`condos.json` 里的指纹不改；意向表数据不进仓库。
- 每条 FR 的验收标准在实现前写进 `docs/ACCEPTANCE.md`，实现后逐条勾。
- 需要交给 Sasha 决定的情形：涉及费用；删除小区；二源冲突无法判断；需要账号或密钥。
